StateQL impact

The prototype separates snapshot metadata from detail retrieval so the normal refresh stays small.

What already exists

StateQL already materializes query rows and exposes bounded result APIs. Pylon does not currently bridge those APIs to this panel.

  • No changerows(handle, { offset, limit }) already returns materialized rows.
  • No changeshow(handle) already returns columns, preview count, row count, storage mode, and expiry.
  • PylonAdd actor-scoped detail and row endpoints. Keep row payloads out of the periodic snapshot.

Optional provenance change

The result store retains original SQL and parameters, but ResultData omits them. Exposing SQL would only recover provenance for retained successful query results, not writes, failures, or expired results.

  • StateQLIf exact SQL is required, add it as an optional, actor-authorized result-detail field after defining retention and redaction.
  • PrivacyDo not return parameters by default. SQL literals and row values may contain sensitive data.
  • Boundsrows() already caps a page at 1,000 compacted rows; Pylon should add a serialized-byte cap and show truncation.

Recommended sequence: ship the Activity timeline and bridge show/rows first. Add SQL provenance only if metadata plus result previews are insufficient. Do not put raw rows in snapshot().
